# 设计：模型切换

## Context

`ocr-engine` 已确立「惰性加载 + 单实例复用」。设计书 §12.1 给出的切换链是「释放旧 → 加载新 → 更新配置」。本设计要解决的是：这条链在失败路径上不成立，且它与在途识别的关系未定义。

## Goals / Non-Goals

**Goals**
- 切换失败不致命，程序保持可用
- 切换不丢弃用户正在等待的识别结果
- 用户始终知道当前结果由哪个模型产出

**Non-Goals**
- 模型下载 / 安装 / 自定义模型导入（设计书 §37）
- 按图像内容自动选模型
- 多模型并行识别对比

## Decisions

### D1：反转设计书 §12.1 的顺序——先加载新，成功后再释放旧

**决定**：

```text
设计书 §12.1（原）                  本变更（修订）
┌─────────────┐                    ┌─────────────┐
│  释放旧引擎  │                    │  加载新引擎  │
└──────┬──────┘                    └──────┬──────┘
       ▼                                  ▼
┌─────────────┐                      ┌────┴────┐
│  加载新引擎  │                   成功│         │失败
└──────┬──────┘                      ▼         ▼
       ▼                       ┌─────────┐ ┌────────┐
   失败 → 无引擎可用            │释放旧引擎│ │保留旧引擎│
   只能重启恢复                 └─────────┘ └────────┘
                                            功能不中断
```

**理由**：加载失败是**会真实发生**的——模型文件损坏、被杀毒软件隔离、磁盘错误、内存不足。原顺序下这些情况都会让程序退化为「有界面但识别不了」，且没有任何自恢复路径，用户唯一的出路是重启。反转后，失败退化为一条提示，用户继续用原模型工作。

**代价**：切换瞬间两个模型同时驻留内存。

**代价为何可接受**：PP-OCRv6 Small 与 Tiny 都是小模型，尖峰是短暂的、量级有限的。用一次可预测的内存尖峰，换取「失败不需要重启」，这笔交易明显划算。若将来引入大模型使尖峰不可接受，可以再引入「低内存模式」作为可选降级——但那时的默认行为仍应是安全优先。

### D2：切换排队等待在途识别，不取消它

**决定**：切换请求到达时若有识别在途，等待其完成再执行切换。

**理由**：用户发起识别后正在等结果。此时切换模型（很可能是因为觉得慢）如果把在途识别取消掉，用户既没拿到结果又白等了一次。让它用旧模型跑完再切换，用户两样都得到。

**与既有机制的配合**：`ocr-execution` 的请求序号机制不需要改动——在途识别是有效请求，其结果正常展示。切换只是在它之后插入。

### D3：切换期间拒绝新识别，而非排队

**决定**：切换进行时发起的识别请求直接拒绝，界面呈现「正在加载模型」，不排队。

**理由**：与 `ocr-execution` 既有的「同一时刻至多执行一次识别」保持同一种风格——拒绝而非排队。排队会让用户在切换完成后突然看到一连串识别被依次执行，行为不可预期。

### D4：枚举时重新扫描，不做哈希校验

**决定**：每次呈现可选模型列表时重新扫描模型目录，只读描述文件并确认文件存在。

**理由**：
- 重新扫描让用户放入新模型后无需重启即可看到，这对免安装的便携程序是很自然的期待。
- 不做哈希校验是因为完整性校验的定位是**获取流程**的一环（`model-assets` 既有需求），用于确认落地文件可信。枚举是一个高频、交互式的操作，对可能数百 MB 的模型文件做逐字节哈希会让打开列表变成一次可感知的卡顿，而收益接近于零——文件在获取时已校验过。

### D5：结果标明产出模型

**决定**：状态区始终标明当前展示结果由哪个模型产出；切换后旧结果保留但标注不变。

**理由**：切换模型的**目的**通常就是对比效果。若切换后状态区直接显示新模型名，用户会把旧结果当成新模型的产出，得到完全错误的对比结论。这个误导恰好发生在用户最需要准确信息的时刻。

### D6：切换失败不写入配置

**决定**：只有切换成功才更新用户配置中的模型标识。

**理由**：若失败也写入，下次启动会尝试加载那个已知有问题的模型，失败后再按回退顺序选择——用户每次启动都要看一次错误提示，而他实际正在用的是回退模型。把失败的选择持久化，等于把一次性的故障变成常驻的噪音。

## Risks / Trade-offs

| 风险 | 影响 | 应对 |
|------|------|------|
| 旧引擎释放不彻底导致内存不回落 | 多次切换后内存持续增长 | 任务 3.4 要求反复切换 20 次并观察内存回落到单模型水平 |
| 切换与在途识别的时序竞争 | 结果错配或崩溃 | 任务 2.3 在识别进行中触发切换并重复多次 |
| 发布产物因第二个模型而增大 | 下载与解压变慢 | 属预期代价，任务 4.2 记录实际增量供评估 |
| 切换期间关闭程序 | 退出时卡住 | 任务 2.5 显式验证 |

## Migration Plan

1. 先扩充模型资产，使系统中真实存在两个模型（否则切换无从验证）
2. 实现枚举，验证列表正确且新放入的模型无需重启即可出现
3. 实现切换的成功路径与失败回滚，先不接界面
4. 接入与在途识别的互斥
5. 接入界面入口与结果模型标注
6. 内存与反复切换的稳定性验证

## Open Questions

- Tiny 与 Small 的实际速度 / 精度差异有多大？这决定了模型切换对用户的实际价值，也影响默认模型的选择。可在任务 4.1 用统一样本实测后回答，不影响任何需求或接口。
