# OCRTool 模型切换

## Why

设计书 §12.1 给出了模型切换的调用链（用户选择 → OCRService.switch_model() → 释放旧 engine → 加载新 engine → 更新配置），§36 将其列入第二阶段，§58 定为 v1.2。

`setup-project-baseline` 建立 `model-assets` 时**刻意**没有实现切换：当时只有一个模型，切换逻辑无处验证，实现了也是死代码。现在引入第二个模型（Tiny）使切换具备实际意义——Tiny 更快但精度更低，Small 更准但更慢，这是用户按场景权衡的真实需求。

本变更的难点不在切换本身，而在 `ocr-engine` 已确立的一条不变量：「单实例复用、禁止重复加载」。切换意味着这个实例要被**替换**，而替换恰好发生在这条不变量最脆弱的时刻——旧实例可能正在被一次在途识别使用，新实例可能加载失败。设计书 §12.1 的调用链把「释放旧」写在「加载新」之前，这个顺序在新模型加载失败时会让程序陷入无引擎可用的状态，必须修正。

## What Changes

### 模型枚举

- `model-assets` 新增枚举能力：返回全部可用模型及其展示名称，供用户选择。
- 每次呈现可选模型列表时重新扫描模型目录，使用户放入新模型后无需重启即可看到。完整性哈希校验仍只发生在获取流程中（既有需求不变），枚举本身不做逐字节校验，因此代价很低。

### 切换语义

- **BREAKING**（相对设计书 §12.1）：调整为**先加载新引擎，确认成功后再释放旧引擎**。设计书原定的「先释放后加载」在新模型加载失败时会让程序既没有旧引擎也没有新引擎，只能重启才能恢复。反转顺序后失败可回滚到旧引擎，用户只看到一条错误提示，功能不中断。
- 代价是切换瞬间两个模型同时驻留内存。PP-OCRv6 Small 与 Tiny 体积都很小，这个尖峰完全可以接受——用一点内存换取失败不致命，是明显划算的交易。
- **MODIFIED**（相对 `ocr-engine`）：「单实例复用」的不变量修订为「任一时刻至多一个引擎实例对外可用」，切换过程中的短暂并存不违反该不变量。

### 切换与在途识别的关系

- 切换请求在有识别在途时排队等待，不取消在途识别。已经发起的识别用旧模型完成并正常返回结果——用户等待的结果不应因为一次切换而丢失。
- 切换期间禁止发起新的识别，界面按既有状态机呈现「正在加载 OCR 模型...」（设计书 §12.1）。
- 切换完成后，已展示的识别结果保留，但状态区标明该结果由哪个模型产出，避免用户误以为当前结果来自新模型。

### 持久化

- 用户选择的模型标识写入用户配置，下次启动沿用。该值仍受 `model-assets` 既有的解析回退顺序保护：若模型被删除，回退到推荐模型并记录错误日志。

## Capabilities

### Modified Capabilities

- `model-assets`: 新增可用模型枚举
- `ocr-engine`: 修订单实例不变量以容纳切换；新增模型切换语义与失败回滚
- `ocr-execution`: 新增切换与识别之间的互斥约束
- `main-window`: 新增模型选择入口与当前模型标识展示

## Impact

- **依赖**：`mvp-image-ocr` 已完成
- **前置条件**：模型资产中需实际存在第二个模型（Tiny）。`packaging/models.lock.json` 与获取脚本需相应扩充，发布产物体积随之增加
- **修改**：`src/ocrtool/ocr/service.py`（切换与回滚）、`models/model_manager.py`（枚举）、`controllers/ocr_controller.py`（互斥）、`ui/` 选择入口与状态区
- **新增配置项**：无新增——沿用 `model-assets` 既有的模型标识配置项
- **修改**：`OCRTool_桌面OCR开发设计书.md` §12.1 的调用链顺序需回写（先加载后释放）
- **不包含**：模型下载与安装、自定义模型导入（属设计书 §37）、按图像内容自动选择模型
