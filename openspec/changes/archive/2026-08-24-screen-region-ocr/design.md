# 设计：屏幕区域截图识别

## Context

设计书 §3.4 只有一张流程图，多显示器与 DPI 完全未涉及。本设计基于对公开实现的调研，其中两个事实决定了方案选型：

1. `QScreen.grabWindow(0, x, y, w, h)` 配合 `virtualGeometry()` 可以一次取到整个虚拟桌面，但返回的图像只携带**一个**缩放比例。混合 DPI 下这个比例对至少一块屏是错的。
2. `QScreen.geometry()` 返回的是**逻辑坐标**，`QScreen.devicePixelRatio()` 给出该屏自身的缩放比例。物理像素矩形需要逐屏用各自的比例换算。

第 1 点是本设计要规避的缺陷，第 2 点是规避它的手段。

## Goals / Non-Goals

**Goals**
- 在任意显示器数量与缩放比例组合下，选区与捕获结果逐像素对应
- 截图结果与既有三种输入完全等价，不新增识别路径
- 任何结束路径都不残留覆盖层

**Non-Goals**
- 跨屏选区（见 D2）
- 延时截图、窗口捕获、滚动截图、贴图（设计书未列入第二阶段）
- 全局快捷键触发（属 `background-residency`）

## Decisions

### D1：先捕获、后选区（冻结帧），而非实时透明覆盖层

**决定**：进入截图流程时立即完成所有屏幕的像素捕获，把捕获到的静态画面作为覆盖层的背景显示，用户在静态画面上框选，最终结果是对该静态画面的裁剪。

**理由**：
- 选区稳定。实时透明层方案下，用户框选期间屏幕内容仍在变化（视频、动画、通知），「看到的」和「截到的」不是同一帧。
- 裁剪退化为纯图像操作，不涉及二次捕获，也就不存在两次捕获之间的时间差。
- 不依赖窗口透明与合成行为，规避了透明覆盖层在不同显卡驱动 / 远程桌面下的表现差异。

**代价**：进入选区前有一次全屏捕获的开销。可接受——捕获是一次性的、量级在几十毫秒。

### D2：逐屏捕获 + 逐屏覆盖层，选区不跨屏

**决定**：为每块 `QScreen` 单独捕获、单独创建覆盖窗口；一次选区限定在按下起点所在的屏幕内。

**坐标换算**（逐屏独立进行）：

```text
                该屏自身的 devicePixelRatio
逻辑坐标(选区) ─────────────────────────────▶ 该屏物理像素坐标
                                                     │
                                                     ▼
                                              从该屏捕获图裁剪
```

**为什么不做整虚拟桌面捕获**：

| 方案 | 混合 DPI 正确性 | 跨屏选区 | 图像质量 |
|------|----------------|---------|---------|
| 整虚拟桌面单次捕获 | ✗ 单一比例必错一块 | ✓ | 副屏被拉伸 |
| 逐屏捕获 + 物理像素拼接 | ✓ | ✓ | ✗ 拼接图像素密度不一致 |
| **逐屏捕获 + 选区不跨屏** | ✓ | ✗ | ✓ 保持原始密度 |

**为什么放弃跨屏选区是合理的**：除了实现代价，跨屏拼接会产生一张内含两种像素密度的图像——同样字号的文字在图中呈现为不同大小，这会直接损害识别质量。也就是说跨屏选区即使实现了，产出也是劣化的。而真实使用中框选内容横跨两台显示器的场景近乎不存在。

**代价**：用户拖动越过屏幕边界时选区被截断。通过选区框在边界处停止的视觉反馈让行为可预期。

### D3：不使用 Qt Multimedia 的 `QScreenCapture`

**决定**：使用 `QScreen.grabWindow()` 路线，明确排除 `QScreenCapture`。

**理由**：`packaging` 的「禁止组件不得进入发布产物」已将 Multimedia 列入禁止清单。为截图引入 Multimedia 会同时违反该需求并显著增加产物体积。这是一条硬约束，不是权衡。

### D4：等待窗口隐藏实际生效再捕获

**决定**：隐藏主窗口后，必须确认隐藏已被系统合成生效，才执行捕获。

**理由**：窗口隐藏是异步的——调用隐藏后立即捕获，画面中大概率仍有主窗口残影。这是截图工具最典型的缺陷，且在开发机上因时序偶然性时隐时现，难以稳定复现。

**实现约束**：不以「固定睡眠若干毫秒」作为唯一手段。固定延时在慢机器上仍会截到窗口，在快机器上又造成无谓卡顿。应以窗口隐藏事件为准，辅以一次事件循环处理，必要时叠加一个下限延时。任务 1.4 需在慢速场景下验证。

### D5：自动复制在非成功路径上必须什么都不做

**决定**：仅在「识别成功且检出文本」时写剪贴板。空结果与错误都不写。

**理由**：写入空字符串不是「没有效果」，而是**清空了用户剪贴板里原有的内容**。用户可能刚复制了一段重要文本，一次没截到字的截图就把它冲掉了，且不可恢复。这是数据破坏，不是体验瑕疵。

### D6：覆盖层生命周期由单一出口保证

**决定**：截图流程的所有结束路径（完成、取消、异常）汇聚到同一个收尾动作，该动作负责销毁全部覆盖层并恢复主窗口。

**理由**：多屏意味着同时存在多个覆盖窗口，它们必须一致地关闭。若分散在各个分支中处理，任何一条被遗漏的路径都会把一个全屏置顶窗口永久留在用户屏幕上——用户除了强杀进程没有别的办法。这个失败模式的严重程度远高于其发生概率，值得用结构保证而非纪律保证。

### D7：完成选区后自动发起识别

**决定**：有效选区完成后直接进入识别，不需要用户再点一次「识别」。

**理由**：截图 OCR 的完整闭环是「截 → 认 → 粘」。中间插入一次确认操作会破坏这个闭环的价值。配合 D5 的自动复制，用户按下截图、框选、松手，文本已在剪贴板中。

**注意**：这使截图成为唯一会自动触发识别的输入方式。打开文件 / 拖拽 / 粘贴仍保持既有行为不变，因为那些场景下用户可能只是想先看看图。

## Risks / Trade-offs

| 风险 | 影响 | 应对 |
|------|------|------|
| 混合 DPI 组合难以在开发机上覆盖 | 缺陷逃逸到用户机器 | 任务 1.6 要求在真实多显示器 + 不同缩放比例下验证；无硬件时至少通过系统缩放设置制造差异 |
| 覆盖层置顶与其他置顶窗口冲突 | 选区界面被遮挡 | 任务 1.5 验证与常见置顶窗口共存 |
| 远程桌面 / 虚拟机下捕获行为异常 | 特定环境不可用 | 列为已知限制，捕获返回空图像时给出可读提示而非崩溃 |
| 选区不跨屏被用户视为缺陷 | 体验反馈 | 边界处的视觉截断使行为可预期；必要时在后续版本重新评估 |
| 自动发起识别使误触代价变高 | 无谓的识别开销 | 由「面积过小视为取消」兜底 |

## Migration Plan

1. 先做捕获与坐标换算，用一个临时入口验证「框选区域 → 保存出的图像内容正确」，此时不接识别
2. 在多显示器 / 不同缩放比例下验证坐标正确性（**本变更的风险集中在此，先于其余工作完成**）
3. 接入主窗口隐藏与恢复，验证捕获画面不含自身
4. 接入取消语义与覆盖层生命周期
5. 接入既有识别管线
6. 最后实现自动复制

## Open Questions

- 选区界面是否需要显示当前选区的像素尺寸？对识别本身无影响，属体验增强，可在实现时按成本决定。
- 面积过小的阈值取多少像素合适？初值取一个保守的小值（如任一边小于 8 物理像素即视为取消），实际使用后按反馈调整。该阈值变化不影响任何需求或接口。
