# 设计：后台常驻与系统集成

## Context

在此之前 OCRTool 是一个纯前台程序：启动 → 窗口 → 关闭 → 退出。托盘、全局快捷键、开机启动三项功能都要求程序在没有可见窗口时继续存在，因此它们共同改写的是**同一个东西**：进程生命周期。设计书 §36 把它们并列为三项功能，掩盖了这一点。

调研公开实现确认了三项机制的可行路径与各自的典型缺陷，本设计围绕这些缺陷展开。

## Goals / Non-Goals

**Goals**
- 同一用户同一目录下唯一实例，且一次崩溃不导致此后无法启动
- 程序在后台运行时用户始终找得到它，也找得到退出它的办法
- 快捷键的任何失败都对用户可见
- 便携目录被移动后开机启动仍然有效

**Non-Goals**
- 多组快捷键、快捷键绑定多种动作
- 开机启动的延迟 / 条件启动
- 完整的通知气泡体系
- 跨平台（本变更的三项机制均为 Windows 特定）

## Decisions

### D1：单实例必须先于其余三项建立

**决定**：实施顺序固定为 单实例 → 托盘 → 快捷键 → 开机启动。

**理由**：见提案中的失效链。三项功能都假设「本进程是唯一的那个」——托盘假设只有一个图标，快捷键假设自己能注册成功，开机启动假设拉起的是唯一实例。先做后三项再补单实例，等于在一个错误的前提上叠三层功能，之后每一层都要返工。

### D2：用本地套接字做单实例，而非仅用互斥量

**决定**：以本地套接字（本机进程间通信端点）承担单实例检测，而非只用一个命名互斥量。

**理由**：互斥量只能回答「是否已有实例」，无法把「用户又双击了一次」这个意图传达给已有实例。而正确的行为不是「第二个实例默默退出」——那样用户双击了图标却什么都没发生，会以为程序坏了。正确行为是**激活已有实例的窗口**，这需要一条通信通道。本地套接字同时提供检测与通道，互斥量只提供前者。

### D3：建立端点前必须清理陈旧残留

**决定**：在监听之前先显式移除同名的遗留端点。

**理由**：这是该方案唯一的严重陷阱。进程被强杀或崩溃时，端点不会被系统自动回收。下次启动时监听同名端点会失败，而失败被解读为「已有实例在运行」——于是程序尝试连接那个无主端点，连接也失败。**结果是程序此后永远启动不起来**，一次偶发崩溃升级为永久性故障，且用户完全无从排查。

清理动作本身是安全的：如果真有实例在运行，它持有的端点不会被这次清理影响到已建立的连接；先尝试连接、连不上再清理，即可区分「活着的实例」与「陈旧残留」。

### D4：实例标识按 用户 + 程序目录 区分

**决定**：端点名称由当前用户与程序所在目录共同派生。

**理由**：
- 按用户区分：多用户机器上，A 用户运行的实例不应阻止 B 用户启动。
- 按目录区分：便携程序放在不同目录的两份副本应能同时运行（例如一份稳定版、一份测试版）。若不按目录区分，第二份会被识别为「重复启动」而弹出第一份的窗口——用户明明双击的是另一个文件夹里的程序，出来的却是别处那个，这非常费解。

**已知后果**：两份副本同时运行时，只有先启动的那份能成功注册全局快捷键，后一份会注册失败。这是可接受的，因为按 `global-hotkey` 的需求，失败对用户可见并给出了原因，行为是可解释的。

### D5：注册式热键，不使用全局键盘监听

**决定**：把组合键注册给系统，由系统在该组合被按下时通知本程序；不安装全局键盘钩子、不使用键盘监听类第三方库。

**理由**（三条独立成立的理由）：
- **隐私**：注册式只在指定组合被按下时收到通知，程序根本接触不到用户的其他按键。监听式则会经手用户输入的一切内容——包括密码。设计书 §43 的隐私立场下，这不是能不能做对的问题，而是不应该获得这个能力。
- **安全软件**：全局键盘监听是键盘记录器的典型特征，极易被杀毒软件拦截或告警。一个 OCR 工具因为快捷键功能被报毒，代价远大于收益。
- **不抢占**：系统的注册接口在组合键已被占用时直接返回失败，不会从其他程序手里夺走热键。这意味着本程序不会破坏用户其他软件的快捷键——这是一个重要的「不作恶」保证。

### D6：保留组合键黑名单

**决定**：维护一份拒绝注册的组合键清单，覆盖通用编辑操作与系统级操作，并要求快捷键必须包含修饰键。

**理由**：全局热键一旦注册，就会从**所有**程序手里截走该组合。用户若把快捷键设成复制或粘贴，整台机器上的复制粘贴都会变成「打开 OCRTool 截图」——而他多半正是想用这个功能去别处粘贴文本。用户不该有能力通过一次设置把自己的系统弄到不可用，这道防线必须在程序里，不能指望用户自觉。

### D7：显式解除「最后一个窗口关闭即退出」

**决定**：关闭界面框架默认的「无可见窗口则退出应用」行为，改由明确的退出路径控制。

**理由**：这是托盘功能的经典陷阱——把主窗口一隐藏，进程就退出了，托盘图标随之消失，表现为「点关闭程序就没了」，而代码里明明写了隐藏。同时，一旦解除该默认行为，就**必须**补上明确的退出入口，否则程序变成杀不掉的常驻进程。两者是一组，不能只做一半。

**启动决策流**：

```text
                    启动
                     │
          ┌──────────┴──────────┐
          │  清理陈旧端点后检测   │
          └──────────┬──────────┘
              ┌──────┴──────┐
        已有实例          无实例
          │                  │
    通知其显示窗口       建立端点、常驻
          │                  │
        本次退出      ┌──────┴──────┐
                   由登录自启       用户手动启动
                      │                  │
                 驻留托盘不显窗口      显示主窗口
                      │
                托盘不可用？→ 显示主窗口（不做隐形进程）
```

### D8：登录启动项每次启动自愈

**决定**：程序启动时若开机启动为开启状态，用当前实际路径重写登录启动项；路径未变化时不重复写入。

**理由**：便携程序**就是会被移动**——用户把文件夹从桌面挪到 D 盘、从 U 盘拷到本地，这是便携形态的正常用法。移动之后登录启动项指向的路径不存在了，开机启动静默失效，用户只会觉得「这功能不好使」。启动时自愈是唯一能在无安装器的前提下解决它的办法，且成本极低。

**已知限制**：若用户直接删除程序目录，遗留的登录启动项无法被清理（程序已经不存在了，也没有卸载器）。该启动项指向不存在的文件，系统会忽略它，无实际危害，但会残留一条注册表记录。这一点应在文档中如实说明。

### D9：注册表写入是程序第一处「自身目录之外」的痕迹

**决定**：在隐私与安全说明中明示程序会写入当前用户的登录启动项，并说明其位置与移除方式。

**理由**：`app-paths` 建立的双根模型的隐含承诺是「程序的一切都在这两个目录里」，用户删掉这两个目录就等于彻底清除。登录启动项打破了这个承诺——它是第一处例外。对一个以「免安装、无残留」为卖点的工具，这个例外必须写明，不能默认用户不在意。

## Risks / Trade-offs

| 风险 | 影响 | 应对 |
|------|------|------|
| 陈旧端点清理逻辑本身有缺陷 | 要么永远启动不了，要么单实例失效 | 任务 1.4 要求反复强杀进程并重启，验证每次都能启动 |
| 解除默认退出行为后出现杀不掉的进程 | 用户只能用任务管理器 | D7 要求退出入口与该改动同批完成，任务 2.5 显式验证 |
| 快捷键在特定安全软件环境下仍被拦截 | 功能不可用 | 注册失败对用户可见（`global-hotkey` 需求），不静默 |
| 开机启动在实际登录场景下的时序问题 | 自启失败或界面异常 | 任务 4.3 要求真实注销 / 重新登录验证，不以模拟替代 |
| 托盘图标在高 DPI 下模糊 | 观感 | 任务 2.1 提供多尺寸图标资源 |
| 常驻后内存长期占用 | 用户观感 | 惰性加载仍然有效，未识别过时不含模型权重；任务 5.2 记录常驻基线内存 |

## Migration Plan

严格按 D1 的顺序，每一步验证通过再进入下一步：

1. **单实例**：检测、激活已有实例、陈旧端点清理。此时程序行为与现在一致，只是不能重复启动
2. **托盘**：图标、菜单、关闭语义、解除默认退出行为、退出入口。此时程序可常驻
3. **快捷键**：注册、冲突处理、黑名单、重新绑定。绑定动作暂定为「显示主窗口」
4. **开机启动**：登录启动项、路径自愈、托盘模式启动
5. 若 `screen-region-ocr` 已完成，将快捷键的绑定动作改为截图识别
6. 常驻稳定性与资源释放验证

## Open Questions

- 默认快捷键取什么组合？设计书 §3.4 提到 `Alt + Shift + A`。该组合是否与常见软件冲突需在任务 3.2 实测确认；若冲突频繁则更换。此决定不影响任何需求。
- 关闭主窗口的默认行为取「隐藏到托盘」还是「退出程序」？倾向于默认退出、由用户主动开启常驻——对一个 OCR 工具，多数用户的心智模型仍是「用完就关」，默认常驻会显得侵入。该默认值可在实现时按体验确定，不影响需求。
