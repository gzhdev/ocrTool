# 设计：识别框绘制

## Context

`mvp-image-ocr` 已确定 `OCRResult` 携带 `scale`，逐行 `OCRLine` 携带四点 `box`，且 `box` 处于**缩放后**坐标系。本变更消费这两个字段。设计书 §17.2 已规定预览区支持滚轮缩放与拖动平移，因此存在第二级、且持续变化的坐标变换。

## Goals / Non-Goals

**Goals**
- 位置框在任意缩放比例与任意预览变换下都贴合文本
- 框与文本可互相定位
- 高行数下预览操作不迟滞

**Non-Goals**
- 框的编辑、按框重新识别、框的导出
- 框的语义分组（段落 / 表格结构）——属设计书 §37

## Decisions

### D1：两级坐标变换分离，不合并系数

**决定**：保持两个独立的变换阶段，识别完成时执行一次「÷ scale」得到原始图像坐标并缓存，此后每次重绘只施加预览区当前的显示变换。

```text
识别完成时（一次性）          每次重绘时（随用户操作）
┌──────────────┐            ┌────────────────────┐
│ box ÷ scale  │──缓存──▶   │ × 视图缩放 + 平移   │──▶ 视口坐标
└──────────────┘            └────────────────────┘
   scale 不再变化               每次滚轮/拖动都变
```

**理由**：两级变换的**变化频率相差数个量级**。`scale` 在一次识别中确定后恒定不变；视图变换随用户每一次滚轮滚动改变。合并成单一系数意味着每次滚轮都要重新引入 `scale`，一旦某条重绘路径漏掉它，框会在用户缩放的瞬间整体错位——而初始状态下看起来完全正常，缺陷极易逃过测试。

**附带收益**：「÷ scale」只做一次，高行数下省去重复计算。

### D2：绘制在呈现层，不写回图像

**决定**：位置框作为预览控件的叠加绘制，不修改图像位图。

**理由**：图像数据是识别的输入，也是用户可能复制或另存的对象。把框烧进像素会污染这份数据，并使「关闭识别框」无法还原。呈现层绘制则天然可切换、可重绘。

### D3：四边形绘制，不取外接矩形

**决定**：按 `box` 的四个角点绘制四边形。

**理由**：外接矩形对倾斜文本会明显偏大，且相邻行的外接矩形会互相重叠，视觉上无法分辨哪个框对应哪一行——这恰好破坏了 D4 联动功能的前提。

### D4：联动以「确认来源」为目的，而非编辑

**决定**：提供框 ↔ 文本行的双向高亮定位，不提供选中后的进一步操作。

**理由**：识别框相对纯文本输出的真正价值是让用户回答「这段文字是从图上哪里来的」——尤其在识别结果有疑问时，用户需要对照原图。双向定位刚好满足这一点。再往上做（点选后单独复制某行、按框重新识别）属于设计书 §37 的范畴，此处不扩张。

### D5：默认关闭识别框

**决定**：`ui.show_boxes` 默认为 `false`。

**理由**：首次使用时纯文本视图更简洁，识别框会在图上叠加大量线条，对「我只想拿到文字」的主流场景是干扰。需要核对来源的用户主动打开即可，且选择被持久化，只需设置一次。

### D6：几何在结果到达时构建一次

**决定**：识别完成时一次性构建全部框的几何数据并缓存，重绘时只做变换与绘制，不重新遍历结果结构。

**理由**：满足「高行数不迟滞」的需求。滚轮缩放会产生密集的重绘，若每次重绘都从结果结构重新解析角点，数百行的开销会直接表现为拖动卡顿。

## Risks / Trade-offs

| 风险 | 影响 | 应对 |
|------|------|------|
| 两级变换在某条重绘路径上被漏掉 | 特定操作后框错位，不报错 | 任务 2.4 要求在「已缩放的大图」上验证缩放与平移的组合，这是唯一能暴露该缺陷的场景 |
| 高行数下重绘开销 | 预览拖动卡顿 | D6 缓存几何；任务 4.1 用高行数样本实测 |
| 框颜色在深色 / 浅色图像上都需可见 | 部分图像上框看不清 | 采用对比度足够的描边样式，任务 3.3 在深浅两类图像上验证 |
| 相邻行框重叠导致联动指向歧义 | 高亮到错误的行 | D3 的四边形绘制已大幅缓解；指向多个框重叠处时取最靠上的一个 |

## Migration Plan

1. 先做「÷ scale」还原与几何缓存，用未缩放的小图验证框贴合
2. 再用触发了尺寸上限的大图验证，确认 `scale` 还原正确
3. 接入预览区的缩放与平移变换，验证组合场景
4. 加入可见性切换与配置持久化
5. 最后做双向联动
6. 高行数性能验证

## Open Questions

- 是否按 `OCRLine.score` 对低置信度的框做视觉区分？信息有价值（能提示用户哪些结果需要核对），但会引入阈值选择问题。倾向于本变更先不做，待实际使用中确认低置信度结果是否常见后再定。该决定不影响任何既有需求。
