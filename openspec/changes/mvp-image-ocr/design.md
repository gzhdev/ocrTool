# 第一版图片 OCR 技术设计

## Context

动机见 `proposal.md — Why`；行为契约见 `specs/`。本文档只记录支撑这些契约的技术决策。

前置依赖：本变更建立在 `setup-project-baseline` 之上，直接消费其 `app-paths`（双根路径）、`app-config`（三层配置）、`app-logging`（隐私约束）、`model-assets`（模型解析）四项能力，不重复设计。

需要纳入考虑的上游事实（在 baseline 阶段实测确认）：

- `rapidocr` 在 2.x → 3.x 发生破坏性变更：调用返回从 `(result, elapse)` 元组变为 `RapidOCROutput` 对象。
- `RapidOCROutput` 在无检出时，`boxes / txts / scores` 三个字段均为 `None` 而非空集合。
- `rapidocr` 持有名为 `RapidOCR` 的独立 logger，会输出识别内容。
- 底层通过 `intra_op_num_threads` / `inter_op_num_threads` 配置推理线程，取值 `-1` 表示交由运行时决定。

设计书中与本变更相关且**已失效**的部分：§13（结果结构缺 `scale`）、§14（合并逻辑未处理空结果）、§22（状态机缺空结果分支）、§26（线程配置字段名与底层不对应）。

## Goals / Non-Goals

**Goals:**

- 把「上游 API 会变」这一已发生的事实，收敛为一处可控的适配边界。
- 让「界面不冻结」与「结果不串图」这两件事由机制保证，而非由调用纪律保证。
- 为后续版本（识别框绘制、模型切换、批量）预留必要信息，但不预先实现其逻辑。

**Non-Goals:**

- 不实现截图 OCR、全局快捷键、系统托盘、设置窗口——设计书 §36。
- 不实现识别框绘制。本变更只保证坐标可还原（`scale` 字段），绘制归后续版本。
- 不实现版面重建：行间距判断、坐标排序、段落与分栏识别、表格检测均不做。
- 不实现图像增强（二值化、锐化、去噪、对比度调整）。设计书 §19 已论证 PP-OCR 对普通截图适应性足够。
- 不实现识别任务的真正中断。

## Decisions

### D1：适配边界收敛在服务层单点

底层引擎实例与其原生返回格式 MUST 只在服务层出现，向上只暴露本项目定义的结果结构。

- **理由不是「架构洁癖」，而是既成事实**：rapidocr 已经破坏性变更过一次。设计书 §47 提出这一约束时是预防性的，现在它是有据可依的。
- **边界的实际宽度**：服务层需要吸收三件事——返回格式差异、`None` 与空集合的差异、第三方 logger 的接管。这三件都与业务无关，放在上层会污染多处。
- **替代方案**：直接在控制器中消费 `RapidOCROutput`。**否决**——上游再次变更时改动面会扩散到控制器与界面。

### D2：`scale` 字段现在就加，即便第一版用不到

结果结构中保留缩放比例字段。

- 设计书 §20 的尺寸上限会使位置框处于缩放后坐标系。第一版不绘制识别框，错位不可见。
- 到实现识别框绘制（设计书 §36）时，若无此字段，症状是「框整体偏移」，而缩放发生在输入阶段、距离绘制代码很远，属于典型的高排查成本缺陷。
- **成本对比**：现在加是一个字段加一次赋值；将来补需要回溯输入路径并修改结果结构的既有消费方。**明显不对称，故现在加**。

### D3：并发控制用「双保险」而非单一手段

```
第一道：线程池容量限制为 1        —— 机制层面杜绝并发进入引擎
第二道：控制器拒绝重入            —— 界面层面立即反馈，禁用触发入口
第三道：请求序号作废              —— 即便前两道将来放开，结果也不会串
```

- **为何不只靠第二道**（设计书 §21 的做法）：那依赖调用方自觉，且默认线程池容量等于 CPU 核数，一旦将来某处绕过控制器直接提交任务，单实例引擎会被并发进入。
- **为何序号机制现在就要有**：第一版界面禁用可以避免串图，但设计书 §58 的 v1.4 批量 OCR 一定会放开并发。届时补序号需要同时改动控制器、工作单元与状态机三处；现在加只是若干行。
- **序号语义**：控制器持有单调递增计数，请求时快照，回调时比对；不相等即丢弃且不产生任何界面副作用（不改状态、不写结果、不解除禁用——解除禁用由当前有效任务负责）。

### D4：状态机增加「空结果」分支

设计书 §22 的五状态无法表达「识别成功但没有文字」。

```
                    ┌──────────────────────────────────────┐
                    ▼                                      │
  空闲 ──▶ 加载模型 ──▶ 识别中 ──┬──▶ 成功 ────────────────┤
   │                   ▲          │                        │
   └───────────────────┘          ├──▶ 空结果 ─────────────┤
      (模型已加载则跳过)           │                        │
                                  └──▶ 错误 ───────────────┘
```

- 归入「成功」会让界面显示「完成 | 0 行」而结果区空白，用户无法区分「没识别出来」与「程序出问题了」。
- 归入「错误」会弹出对话框，但截图中没有文字是完全正常的用户操作，弹窗是过度反应。
- 因此单列一态，界面反馈为状态区提示「未识别到文本」。

### D5：跨线程传递结果使用通用对象类型

工作单元向主线程投递结果时，信号签名使用通用对象类型而非具体的结果类。

- **原因**：PySide6 的信号类型系统不接受任意 Python 数据类作为签名类型，直接以结果类声明会在连接阶段失败。
- 签名同时携带请求序号与结果对象，与 D3 的作废机制配套。

### D6：线程数配置做一层映射

设计书 §26 的 `runtime.cpu_threads` 无法直接传给底层——底层读取的是引擎配置中的 `intra_op_num_threads` / `inter_op_num_threads`。

- 服务层负责把本项目的配置项映射为底层配置项。
- 默认策略沿用设计书 §26 的 `min(4, 逻辑核心数)`；配置为 0 或负值时传 `-1`，交由推理运行时自行决定。
- 第一版不开放界面调节，仅配置文件可改。

### D7：预览显示原图，识别使用缩放副本

尺寸上限只作用于送入识别的副本，预览始终显示原始图像。

- 若预览也用缩放图，用户放大查看时会看到二次插值的模糊结果，且与「原图」的心理预期不符。
- 代价是超大图时内存中同时存在两份图像数据。上限 6000 像素下这一开销可接受，且识别副本在识别结束后即可释放。

### D8：图像数据流

```
QImage (输入: 文件/拖放/剪贴板)
   │
   ├──▶ 预览区                      (原始尺寸)
   │
   └──▶ 尺寸检查 ──▶ 等比缩放 ──▶ ndarray ──▶ 服务层 ──▶ 引擎
                       │
                       └──▶ scale 随结果返回
```

全程不落磁盘（设计书 §44）。剪贴板与拖放路径同样走此流程，无特例。

## Risks / Trade-offs

- **识别任务无法中断** → 大图或高密度文本时用户只能等待，界面虽响应但触发入口禁用。缓解：状态区显示进行中状态使等待可预期；D3 的序号机制保证等待结束后不会看到错误的结果。真正的中断能力待后续版本评估。
- **单线程池限制吞吐** → 第一版为单图交互场景，无吞吐需求。批量场景（设计书 §58 v1.4）需重新评估容量与引擎实例数的关系，届时 D3 的第三道保险开始发挥作用。
- **服务层适配边界随上游变更而膨胀** → 若上游再次大改，适配代码可能变复杂。缓解：适配逻辑集中且有集成测试覆盖，复杂度可见；必要时可整体替换实现而不影响上层。
- **`scale` 字段在第一版无消费方** → 存在被后续开发者当作冗余删除的风险。缓解：在结果结构定义处以注释说明其用途与来源，并由单元测试断言缩放场景下该字段取值正确。
- **预览与识别双份图像数据** → 超大图时内存翻倍。缓解：识别副本为局部对象，识别结束即释放；连续 100 次识别的稳定性测试可暴露泄漏。

## Migration Plan

无存量行为需迁移。落地顺序遵循设计书 §53 的分阶段思路，但将可独立验证的部分前移：

1. 结果结构与服务层适配（含空结果规范化、第三方 logger 接管）。此步可脱离界面，用命令行驱动一张样本图完成端到端验证。
2. 工作单元、控制器、状态机与序号机制。此步可用无界面的信号测试验证「不阻塞」与「过期丢弃」。
3. 图像输入与校验、尺寸上限与缩放。
4. 主界面组装、状态区、错误分级、启动自检。
5. 稳定性验证：连续 100 次识别观察内存与模型加载次数。
6. 回写设计书 §13 / §14 / §22 / §26。

回滚：各步骤均为新增模块，失败可丢弃该步产物；第 1 步产出的服务层若被推翻，后续步骤均未开始，损失可控。

## Open Questions

- **推理线程数的最优默认值**。设计书 §26 给出 `min(4, 逻辑核心数)`，但未经实测。此问题不影响结果契约与任务拆分，可在功能完成后通过基准测试（设计书 §39）调整默认值，属于配置项调优。
